# アーキテクチャと実装解説

AutoExtract の全体構成と、主要な機能の仕組みを説明します。

## 全体構成

![architecture](imgs/architecture.drawio.png)

AutoExtract は、フロントエンド、バックエンド、インフラの 3 層で構成されます。フロントエンドは React 製の SPA で、CloudFront と S3 で配信します。バックエンドは FastAPI を Lambda で動かす REST API です。どちらも認証には Cognito を使います。インフラは AWS CDK（TypeScript）で定義し、機能ごとに構成を分けています。

利用している主な AWS サービスは以下のとおりです。

| サービス                | 役割                                                                                      |
| ----------------------- | ----------------------------------------------------------------------------------------- |
| Cognito                 | ユーザー認証。ログイン時にユーザー情報をデータベースへ同期します                          |
| SageMaker               | OCR エンジンの推論エンドポイント。アクセスがないときはインスタンスを 0 台まで縮小できます |
| Bedrock                 | 情報抽出とスキーマ生成に使う LLM                                                          |
| Bedrock AgentCore       | 抽出結果を検証するエージェントの実行基盤                                                  |
| Aurora DSQL / DynamoDB  | データストア。用途を分けて併用しています（後述）                                          |
| Step Functions          | OCR から抽出までの処理フローの制御                                                        |
| API Gateway (WebSocket) | 閲覧中のユーザー表示などのリアルタイム連携                                                |
| CloudFront / WAF        | フロントエンドの配信とアクセス制御                                                        |

## ユースケースと処理の流れ

AutoExtract では、帳票の種類ごとに **ユースケース** を用意します。ユースケースは「どんな項目を、どう抽出し、どう検証するか」をまとめた単位です。まずユースケースを作成し、そのユースケースに対して帳票をアップロードして処理する、という 2 段階で使います。

### ユースケースの作成

新しいユースケースを作るときは、サンプルの帳票をアップロードすると、LLM が抽出項目（スキーマ）を自動で生成します。生成されたスキーマは専用の画面で確認でき、項目の追加や編集ができます。

スキーマの各項目には、名前と表示名のほか、型を指定します。型は次の 4 種類です。

| 型       | 用途                                                                 |
| -------- | -------------------------------------------------------------------- |
| `string` | 文字列。氏名や住所などの一般的な項目                                 |
| `number` | 数値。金額や数量など                                                 |
| `map`    | 複数の項目をまとめた入れ子の構造。子となる項目を内部に持ちます       |
| `list`   | 同じ形式の項目の繰り返し。明細行のように、件数が可変な項目に使います |

`map` と `list` を使うことで、明細のある帳票のような入れ子の構造も表現できます。例えば、見積書のスキーマは次のように定義できます。

```json
{
  "fields": [
    { "name": "quote_number", "display_name": "見積No.", "type": "string" },
    {
      "name": "client_info",
      "display_name": "宛先情報",
      "type": "map",
      "fields": [
        { "name": "company_name", "display_name": "会社名", "type": "string" },
        { "name": "address", "display_name": "住所", "type": "string" }
      ]
    },
    {
      "name": "items",
      "display_name": "見積明細",
      "type": "list",
      "items": {
        "type": "map",
        "fields": [
          { "name": "description", "display_name": "項目", "type": "string" },
          { "name": "amount", "display_name": "金額", "type": "number" }
        ]
      }
    }
  ]
}
```

このスキーマは、LLM による自動生成の結果をそのまま使うほか、画面上で項目の追加や削除、名前や型の変更ができます。

スキーマに加えて、ユースケースごとに次の設定を行います。

**入力方法**（帳票の取り込み方）。両方を同時に有効にもできます。

| 入力方法             | 内容                                              |
| -------------------- | ------------------------------------------------- |
| ファイルアップロード | 画面から画像や PDF をアップロードして取り込みます |
| S3 同期              | 指定した S3 の場所に置かれた帳票を取り込みます    |

**エージェント検証**（抽出結果をエージェントに検証させるか）。

| 設定           | 内容                                                                                 |
| -------------- | ------------------------------------------------------------------------------------ |
| 有効 / 無効    | このユースケースでエージェント検証を使うか                                           |
| 自動実行       | 有効にすると、抽出の後に検証を自動で実行します。無効の場合は画面から手動で実行します |
| 使用するツール | 検証に使うツールを選びます                                                           |

このほか、作成したユースケースは、ユーザーやグループに権限を与えて共有できます（後述の権限設計を参照）。

### 帳票の処理

作成したユースケースに対して帳票をアップロードすると、その帳票が処理されます。バックエンドは画像レコードを作成し、Step Functions を起動します。Step Functions は、各帳票に対して、まず OCR で文字を読み取り、続いてスキーマに沿って情報を抽出します。ユースケースでエージェント検証を有効にしている場合は、抽出の後に検証を実行します。

抽出した結果は画面で確認でき、誤りがあれば手動で修正できます。

複数ページの PDF をアップロードするときは、処理方法を選択できます。

| モード           | 処理内容                                                                 | 主な用途                             |
| ---------------- | ------------------------------------------------------------------------ | ------------------------------------ |
| 全ページ統合処理 | 複数ページを 1 つの画像として結合し、まとめて 1 つの抽出結果を生成します | 1 枚の帳票が複数ページにまたがる場合 |
| ページ別個別処理 | 各ページを個別に処理し、ページごとに抽出結果を生成します                 | 1 ページが 1 枚の帳票にあたる場合    |

なお、PDF の変換や S3 からの一括取り込み、スキーマの自動生成といった時間のかかる処理は、API から切り離した非同期の Lambda で実行します。API Gateway の 29 秒のタイムアウト内に収まらない場合があるためです。

## データストアの使い分け

AutoExtract は Aurora DSQL と DynamoDB を併用し、扱うデータによって使い分けています。

| データストア | 格納するデータ                                                                             | 特徴                                                             |
| ------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| Aurora DSQL  | ユーザー、グループ、ユースケース、ツールと、それらの権限                                   | 互いに参照し合う関係を持つデータを、リレーショナルに扱います     |
| DynamoDB     | 画像レコード、エージェント検証のジョブ、ユースケースのスキーマ定義、ユーザーごとの設定など | OCR 結果のように構造が一定しないデータを、スキーマレスに扱います |

ユースケースは両方のデータストアにまたがります。スキーマ定義の本体は DynamoDB に、権限管理のための情報は Aurora DSQL に置き、両者を `app_name` で対応づけます。

## 権限設計

権限は、ユーザーそのものに与えるシステムロールと、ユースケースごとに与える権限の 2 軸で構成します。

システムロールは、ユーザーが AutoExtract 全体に対して何をできるかを表します。`reader`、`author`、`admin` の 3 種類があり、この順に権限が広くなります。

| ロール   | できること                                                                                                 |
| -------- | ---------------------------------------------------------------------------------------------------------- |
| `reader` | 共有されたユースケースを利用できます。新しいユースケースの作成はできません                                 |
| `author` | ユースケースを新しく作成できます。デプロイ直後の既定のロールです                                           |
| `admin`  | すべての操作に加えて、管理画面（ユーザー、グループ、ユースケース、ツール、全画像の管理）にアクセスできます |

ユースケース権限は、あるユースケースに対して何をできるかを表します。ユースケースを共有するときに、ユーザーまたはグループへ与えます。`viewer`、`editor`、`owner` の 3 種類があり、この順に権限が広くなります。

| 権限     | できること                                                                      |
| -------- | ------------------------------------------------------------------------------- |
| `viewer` | 帳票のアップロード、OCR や抽出結果の確認と修正、エージェント検証の実行          |
| `editor` | `viewer` の操作に加えて、スキーマやツール割り当てなど、ユースケースの設定の変更 |
| `owner`  | `editor` の操作に加えて、ユースケースの削除や共有の管理                         |

`viewer` は閲覧だけでなく、日々の帳票処理と抽出結果の修正までを行える点に注意してください。ユースケースそのものの設定を変えるには `editor` 以上が必要です。

あるユーザーが特定のユースケースに対して持つ権限は、次のように決まります。`admin` ロールのユーザーは、ユースケース権限に関わらず、すべてを許可されます。それ以外は、ユーザーへ直接与えた権限と、所属するグループを通じて与えた権限のうち、最も強いものを採用します。ただし `reader` ロールのユーザーは、`editor` 以上を必要とする操作（ユースケースの設定変更など）はできません。

## エージェント検証

エージェント検証は、Bedrock AgentCore 上のエージェントが、原本の帳票と抽出結果を照合し、ツールで正しさを確かめたうえで修正候補を提案する機能です。エージェントには原本の画像と抽出結果を渡します。エージェントは、ツールで裏付けの取れた誤りだけを、次の形式の修正候補として返します。返された候補は抽出結果の画面に一覧で表示され、利用者が 1 件ずつ受け入れるか却下するかを選べます。

```json
{
  "suggestions": [
    {
      "field": "total_amount",
      "original_value": "479,520",
      "suggested_value": "475,200",
      "reason": "小計 440,000 と消費税 35,200 の合計は 475,200 です",
      "confidence": "high",
      "tool_used": "verify_total_with_tax_calculation"
    }
  ]
}
```

検証は、ツールを公開する Gateway と、検証を実行する Runtime で構成されます。Runtime 上のエージェントが Gateway に接続し、そのユースケースに割り当てられたツールを使って検証します。ツールを 1 つも割り当てていない場合は、ツールを使わず LLM 単体で検証します。なお、検証の結果は LLM の性質上、同じ入力でも実行ごとに変わることがあります。

### ツールの追加と権限管理

検証に使うツールは Lambda として実装し、Gateway のターゲットとして登録します。登録したツールは Aurora DSQL に自動で同期され、管理画面から扱えるようになります。ツールの利用は、次の 2 段階で制御します。

| 段階                     | 制御の内容                                                                                                                 |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| ツールを誰に見せるか     | ツールをユーザーやグループに割り当てます。割り当てられた人だけが、そのツールを扱えます（管理者はすべてのツールを扱えます） |
| ユースケースで何を使うか | ユースケースに対して editor 以上の権限を持つ人が、自分に見えるツールの中から、そのユースケースで使うツールを選びます       |

この 2 段階により、権限のないユーザーが、見えないはずのツールをユースケースに紛れ込ませることを防いでいます。

なお、可視性の制約が効くのはユースケースへの割り当て時だけです。いったんユースケースに登録されたツールは、そのユースケースで検証を実行する人であれば、そのツールが個人に見えるかどうかに関わらず利用できます。
